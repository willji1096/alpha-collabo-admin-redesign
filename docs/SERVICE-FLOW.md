# 알파콜라보 — 서비스 흐름 (Service Flow)

> 작업 기준 단일 문서. 화면 기능·UX 결정 시 항상 이 흐름에 맞는지 확인한다.
> 우리 작업 범위는 **브랜드사 어드민(웹) + app/phone** 뿐이다.

---

## 1. 등장 주체 (Actors)

| 주체 | 설명 |
|---|---|
| **알파콜라보 매니저/운영** | 캠페인 생성, 전체 브랜드·인플루언서·정산 총괄. 인플루언서 소통 중개. |
| **브랜드사 (광고주 / 클라이언트)** | 캠페인의 실제 주인. 지원자 관리·선정·운영. **우리 어드민의 실사용자.** |
| **인플루언서** | 캠페인에 지원/수락하고 콘텐츠 제작. **회사 자산** — 브랜드사와 직접소통 금지(매니저 경유). |

> 계정은 알파콜라보가 발급한다. 브랜드사 어드민에 계정설정/프로필 생성 기능을 만들지 않는다.

---

## 2. Surface 4개 (혼동 금지)

| Surface | 사용자 | 역할 | 우리 작업 |
|---|---|---|---|
| **최고관리자 어드민** | 알파콜라보 매니저/운영 | **캠페인 생성**, 전체 브랜드·인플루언서·정산 총괄 | ✗ |
| **브랜드사 어드민 (웹)** | 브랜드사 | 자기 캠페인 신청서 관리·탐색·선정·운영 | ✅ |
| **app/phone** | 브랜드사 | 위 어드민의 모바일판 | ✅ |
| **알파콜라보 앱** | 인플루언서 | 캠페인 보고 **지원** | ✗ (별개, `../앱/`) |

핵심: **어드민이 2개다.** 매니저가 캠페인을 만드는 곳은 *최고관리자 어드민*이고, 우리가 만드는 건 브랜드사가 운영하는 *브랜드사 어드민*이다. 그래서 우리 어드민엔 풀스펙 "캠페인 생성" 기능이 없는 게 맞고, 무게중심은 **신청서 관리 + 인플루언서 탐색**에 있다.

---

## 3. End-to-End 흐름

```
[최고관리자 어드민]                [알파콜라보 앱]              [브랜드사 어드민 = 우리]
   매니저가 브랜드사 상담      →   캠페인이 인플루언서에게   →   지원자들이 신청목록에 집계
   → 캠페인 생성                   노출 → 인플루언서 지원         → 브랜드사가 선정·검수·완료
```

1. 브랜드사 ↔ **매니저 상담** → 매니저가 **최고관리자 어드민에서 캠페인 생성**
2. 캠페인이 **알파콜라보 앱(인플루언서용)** 에 등록·노출
3. 인플루언서가 알파콜라보 앱에서 **지원** (예: 10명 모집에 다수 지원)
4. 지원자들이 **브랜드사 어드민 → 신청서 관리(신청목록)** 에 집계됨
5. 브랜드사가 어드민에서 **선정(리뷰어 선정)** → 검수 → 수정 → 등록완료 운영
6. (병행) 브랜드사가 **인플루언서 탐색/방문 예정**에서 능동 제안 (매니저 경유)

> 따라서 **신청목록 = "알파콜라보 앱에서 우리 캠페인에 지원한 인플루언서들"**.
> 신청목록 카드의 주체는 캠페인이 아니라 **지원한 인플루언서** → 카드는 인플루언서를 주인공으로(아바타/핸들 강조) 잡는 게 구조에 맞다.

---

## 4. 신청서 관리 파이프라인 (브랜드사 어드민 핵심)

성공 본류:
```
신청 ── 선정 ── 검수 ── 수정 ── 완료
```

| 단계 | 페이지 | 핵심 액션 |
|---|---|---|
| **신청** | list.html (신청목록) | 지원자 확인 → `리뷰어선정` / `리뷰어 미선정` |
| **선정** | list-selection.html (선정목록) | 배송정보 입력 → 인플루언서가 콘텐츠/초안 제출 |
| **검수** | list-inspection.html (검수요청목록) | `리뷰 검수`(컨펌→완료) / `초안수정요청`(→수정) / `미방문` |
| **수정** | list-revision.html (수정요청목록) | 재제출 후 다시 `리뷰 검수` |
| **완료** | list-completed.html (등록완료목록) | 최종 (terminal) |

이탈/제외 분기 (본류에서 빠진 건들):
- **미선정** (list-unselected) — 신청했으나 선정 안 됨
- **선정후 취소** (list-cancel-selected) — 선정 뒤 취소
- **인플루언서 취소** (list-cancel-influencer) — 인플루언서 본인 이탈

> 검수 ↔ 수정은 루프(초안수정요청 시 수정으로 갔다가 재검수). 이탈 3종은 단계 바에 넣지 않고 별도 처리.

---

## 5. 인플루언서 탐색 라인 (브랜드사 능동 영업)

"지원을 기다리는" 신청서 관리와 반대로, 브랜드사가 먼저 인플루언서를 찾아 제안하는 라인.

| 메뉴 | 페이지 | 역할 |
|---|---|---|
| **인플루언서 탐색** | influencer-search.html | 전체 풀을 조건(국적·플랫폼·팔로워·성별·방문예정일)으로 검색 → 제안/저장 |
| **방문 예정** | visit-planned.html | **타 캠페인으로라도 한국 방문 일정이 잡힌 인플루언서 전체.** "기왕 온 김에 우리 것도" 끼워파는 능동 영업 핫리스트. 방문비용 장벽 해결돼 매칭 쉬움 |
| **저장한 인플루언서** | saved-influencer.html | 찜해둔 후보 모음 |

---

## 6. 정책 / 제약 (위반 금지)

- **캠페인 생성**은 매니저(최고관리자 어드민) 영역 — 브랜드사 어드민/앱에 풀스펙 생성 기능 임의 확대 금지.
- **인플루언서 직접소통 금지** — 회사 자산. 브랜드사↔인플루언서 직접 채팅/메시지 UI 금지, 소통은 매니저 경유. (앱은 4탭, influencer-chat/manager-chat/메시지탭 없음)
- **계정**은 알파콜라보 발급 — 계정설정/프로필 편집 페이지 만들지 않음.
- 샘플 데이터: 국기 이모지 금지(country-code 칩), 테스트성 이름 금지, 어드민에 없는 데이터 날조 금지.

---

## 7. 작업 함의 (Design/UX)

- 우리 surface(브랜드사 어드민+앱)의 무게중심 = **신청서 관리(운영) + 인플루언서 탐색(영업)**.
- 신청목록 등 "지원자" 화면의 주인공은 **인플루언서**.
- 단계(파이프라인)는 메뉴가 아니라 "순차 흐름"으로 읽히게 (어드민: 단계 바 / 앱: pill-tabs).
- 캠페인 "생성"보다 "운영·선정·검수" 동선 완성도가 우선.
